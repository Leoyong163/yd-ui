# 组件库拆分可行性评估

> 配套文档：`docs/前端样式与质量体检报告.md`（样式质量问题清单）
> 相关真源：`src/theme/tokens.ts`、`scripts/gen-tokens.mjs`

## 一、结论

**方案可行，但要先纠正一个前提**：在这个项目里，「把系统的所有组件拉出来」不是一次提取，而是两个难度完全不同的动作叠在一起。

| 动作 | 对象 | 难度 | 说明 |
| --- | --- | --- | --- |
| **真·提取** | 已有的 12 个组件 + 652 个类名的样式配方 + 设计令牌 | 低，机械性劳动 | 边界清楚，靠脚本可核对 |
| **先造出来** | 目前以「类名 + 内联样式」散落在页面里的那些 UI | 中高，需要设计裁决 | 这些 UI 没有组件形态，只有 markup |

原因：这个系统的组件层很薄，而组件的外观大部分**不由组件实现**——它由全局 CSS 的类名决定。所以「抽出组件」抽不出外观，除非连样式一起搬。

### 实测底数

| 指标 | 数值 | 含义 |
| --- | --- | --- |
| `.vue` 文件 | 48 | 12 在 `src/components/`，32 在 `src/pages/`，4 个在根目录与 `devtools/` |
| 含 `<style>` 块的 `.vue` | **0** | 组件与样式零封装，只靠类名隐式耦合 |
| CSS 类名（去重） | **652** | 分布在 7578 行 CSS 里 |
| 无任何引用的类名（死 CSS） | **198**（30%） | `components.css` 201 个里 103 个是死的（51%） |
| 不可静态判定的类名 | 33 | 由模板串拼装，需人工核对 |
| 用了但任何 CSS 都没定义（幽灵类名） | **18** | markup 上的类名指向空 |
| 同时定义在两个样式表的类名 | **46** | `components.css` 与 `pages.css` 同名，后者恒胜（含 `layout.css`/`base.css` 的重复共 59） |
| 页面内联 `style="…"` | **519 处** | 分布在 30 个文件 |
| 完全重复的内联样式 | **288 处** | 77 组，其中一组重复 20 次 |
| 没有任何地方 import 的组件 | **4 个** | `IconTile` / `UrgencyTag` / `PortalMenu` / `RoleAuthDropdown` |

## 二、三个阻塞点

### 阻塞点 1：组件不自带样式

48 个 `.vue` 里 **0 个**写 `<style>`。组件与全局 CSS 只靠 class 名隐式耦合：CSS 改个类名，Vue 模板静默失效，没有任何编译期保护。

具体到组件层：`src/components/` 的 12 个组件一共只用到 **39 个类名**，其中 **29 个与页面目录共享**，只有 10 个是组件独占（`empty-state` `kpi-asset` `pagination` `pagination-info` `pagination-pages` `page-btn` `pagination-size` `pagination-jump` `tree-owned` `tree-denied`）。也就是说组件几乎没有自己的样式词汇表：

| 组件 | 越界依赖（定义在 `pages.css`，或与 `pages.css` 双重定义） |
| --- | --- |
| `PermissionTree.vue` | 7 个类里 6 个越界：`perm-tree` `tree-toolbar` `tree-toolbar-btn` `tree-list` `btn` `btn-ghost` |
| `PermissionTreeRows.vue` | 9 个类里 8 个越界：`tree-row` `tree-level-*` `tree-toggle` `leaf` `tree-name` `tree-type` `tree-children` `tree-owned` `tree-denied` |
| `Pagination.vue` | 9 个类里 1 个越界：`active` |
| `SearchBox.vue` | 3 个类里 1 个越界：`search-box` |
| `KpiImg.vue` | 1 个类全越界：`kpi-asset` |
| `StatusTag.vue` / `UrgencyTag.vue` | 1 个类全越界：`tag` |

**结论：现在搬走组件，引用方必须同时引入全局 CSS，「独立引用」是假独立。**

### 阻塞点 2：46 个类名双重定义，且 `components.css` 恒输

`src/styles/index.css` 的加载顺序是 `components.css`（第 9 行）→ `pages.css`（第 10 行）。同名类名，后加载者胜。

**所以 `components.css` 不是组件样式的真源，它是一份「被部分覆盖的旧稿」。**

46 个冲突类名：

```
btn  btn-primary  btn-secondary  btn-ghost  btn-danger  kpi-asset
form-field  full  textarea  search-box  perm-tree  tree-row  tabs  tab  active
tag  card-header  card-title  card-body  table-wrap  table  cell-name  selected
actions  danger  toast-root  success  col-panel  col-panel-body  list-item
list-item-title  list-item-meta  tree-toolbar  tree-list  highlight
tree-toggle  leaf  tree-children  tree-name  tree-type  tree-owned  tree-denied
tree-level-1  upload-zone  stat-icon  error-summary
```

其中 `btn*` `tag` `card-*` `table*` `tab` `active` `selected` 属于**控件语义**，天然该归组件库；`col-panel*` `list-item*` `table-wrap` 属于**页面布局语义**，该留宿主。

**这一步不能跳过**：整文件搬运 `components.css` 会让依赖 `pages.css` 覆盖的那部分外观发生变化。

### 阻塞点 3：198 个死类名会把包袱带进库里

`components.css` 的 201 个类名里 **103 个没有任何引用**（`btn-lg` `spinner` `dot` `icon-sun` `is-loading` `btn-danger-ghost` `btn-icon` `icon-3d-*` 等），`pages.css` 449 个里 87 个，`layout.css` 54 个里 11 个。

另有 **33 个类名不可静态判定**（由模板串拼装，如 `` `icon-tile-${tone}` ``、`` `tag ${cls}` ``），必须人工核对前端是否还在用——其中 `IconTile` 的 `tone`/`size` 枚举（`blue` `cyan` `purple` `orange` `green` `rose` / `sm` `lg`）与 `shared.ts` 的状态映射表是已知的取值空间。

**整文件搬运 = 把一半的包袱发布出去；顺手删除 = 有误删风险。必须先裁决。**

### 附：4 个组件已经存在，但没有任何地方在用

`IconTile` `UrgencyTag` `PortalMenu` `RoleAuthDropdown` 的 import 入度为 0。同时页面里手写着等价实现绕过它们：

- `Apply.vue` 手写 `` `flow-card-icon icon-tile icon-tile-${TONES[...]}` ``，而不是用 `<IconTile>`
- 各页面手写 `` `tag ${urgencyTagClass(...)}` ``，而不是用 `<UrgencyTag>`

**这暴露了「组件已存在但没被采用」的真问题。抽库会立刻把它变成显性问题：库里会有 4 个没人用的组件，而它们的等价实现散在 7 个页面里。**

### 附 2：18 个幽灵类名 —— markup 上的类名指向空

这些类名被模板使用，却在任何 CSS 里都没有定义：

```
user-picker-control  user-picker-chip  user-picker-list  tag-blue
system-roles-group  permission-col-head-systems  permission-col-head-roles
post-label-date-body  expanded-row-details  subitem-dropdown-wrapper  …
```

它们的作用完全靠**同行内联样式**撑着，例如（7 个表单页各一份）：

```html
<div class="user-picker-chip"
     style="display:flex;align-items:center;gap:6px;background:var(--surface-3);
            padding:4px 10px 4px 4px;border-radius:20px;border:1px solid var(--border)">
```

**这是「组件不存在」的直接证据：类名只是占位，真正的样式写死在每一处 markup 里。**`user-picker-chip` 这 6 项内联样式在 7 个文件里逐字重复。

## 三、目标结构

```
宿主应用 宿主工程/
├── src/pages/            32 个路由页面（业务，不进库）
├── src/App.vue           antd 主题桥（宿主侧的运行时合同）
└── packages/ui/          ← 抽出来的系统组件库
    ├── src/theme/tokens.ts     唯一令牌真源（亮/暗）
    ├── src/styles/             样式配方（控件语义）
    ├── src/components/         通用组件
    ├── src/business/           业务组件（UserPicker 等）
    └── docs/                   设计规范（从真源生成）
```

**依赖方向必须单向：`pages → ui`。库不得 import `pages/**`，也不得依赖宿主的 `src/shared.ts`。**

## 四、三步路线

### 第 1 步 —— 裁决类名归属（不写代码，只产出归属表）

输入：46 个同名类 + 198 个死类 + 33 个不可判定类。

输出：**已产出 `docs/类名归属裁决表.md`** —— 覆盖全部 652 个类名，按决策分组（删除候选 198 / 人工核对 33 / 同名冲突 51 / 归组件库 37 / 归宿主 302 / 基础层 31），每条带「定义于 + 组件用 + 页面用 + 入口用」的用量证据。由 `scripts/gen-class-ownership.cjs` 生成，改完代码可重跑刷新。

判定规则建议：

- 被 ≥2 个组件使用、且与页面业务语义无关 → 归 `ui`（`btn*` `tag` `card-*` `table*` `tab` `active` `selected` `input` `select` `modal*`）
- 强页面语义 → 留宿主（`col-panel*` `list-item*` `table-wrap` `form-block-system` `system-roles-group`）
- 死类 → 单独一张删除清单，先确认无动态引用再删

**验证门：归属表的每一行都能指出「谁在用」，无孤行。**

### 第 2 步 —— 建库并搬纯组件

先只搬**零依赖**的组件，跑通引用链：`Icon` `StatusTag` `EmptyState` `OverflowTooltip` `Modal` `Pagination` `SearchBox` `KpiImg`，以及 `PermissionTree` + `PermissionTreeRows`（需一并搬走它依赖的 `pages.css` 类）。

同时决定 4 个孤儿组件的去留：`IconTile` / `UrgencyTag` 应该**启用**（它们是页面里手写实现的正确归属），`PortalMenu` / `RoleAuthDropdown` 需确认是否是废弃草稿。

**验证门：亮/暗双主题截图对比，改动前后像素级一致；生产构建通过。**

### 第 3 步 —— 用重复数据反过来定组件边界

这是最容易见效的一步，因为**重复处已经替你标出了组件边界**：

| 重复组 | 次数 | 应抽成的组件 |
| --- | --- | --- |
| 用户选择弹窗区块（约 70 行 markup + 内联样式） | ×7 | `UserPicker` |
| `user-picker-chip`（含 6 项内联样式的一行 div） | ×7 | `UserChip` |
| `system-pick-item` 系统选择项 | ×7 | `SystemPicker` |
| `role-form/Create\|Delete\|ModifySection` 三个近亲文件 | ×3 | 合并为一个 `RoleSection` + `mode` prop |
| 表格列宽内联样式（`min-width: 120px/160px/44px/56px`） | ×9/×5/×4/×3 | 列宽令牌或 `TableCol` |

**这 288 处重复里，每一处都对应一个尚未被抽象出来的组件。**

## 五、两种落地形态

| | A. workspace 内独立包 `packages/ui`（推荐） | B. 仓内目录 `src/design-system/` |
| --- | --- | --- |
| 独立引用 | 是，`import { Button } from '@yd/ui'` | 否，仍是应用的一部分 |
| 增删改 | 在 `packages/ui` 内改，宿主自动生效 | 同一仓内改，天然同步 |
| 同步机制 | workspace 依赖，无需发版 | 无需同步 |
| 成本 | 需配 workspace、包构建、路径别名 | 几乎为零 |
| 适用 | 要给多个项目共用 | 只服务当前系统 |

**建议：先按 A 建，但暂不发布到私有 registry。** 契约稳定前发版会立刻陷入「改一处 → 发版 → 升依赖」的循环；workspace 协议已经能提供「独立引用 + 可增删改 + 自动同步」的全部好处，且零版本管理成本。

## 六、风险清单

1. **双份并存期最危险。** 库里的组件与页面里的旧实现会同时存在。必须按模块逐个切换 + 截图回归，不能一把切。
2. **没有回归测试。** 项目无单测、无视觉基线。当前唯一可用的手段是浏览器实测计算样式 + 截图对比（可复用 `~/.workbuddy/skills/frontend-measure-audit/scripts/measure.cjs`）。
3. **库与宿主的运行时合同必须显式化。** 库消费令牌，宿主要负责主题切换（`data-theme`）与 antd 桥（`ConfigProvider theme`）。这个合同若不写清，引用方少配一项就静默降级——本项目已经踩过同一个坑（`App.vue` 的 antd 桥搭了一半）。
4. **46 个类名的归属需要设计判断，不能纯靠脚本。**
5. **设计规范文件必须与代码同源生成。** 手写的规范三周后就会漂移，这正是 `App.vue` 里 antd 令牌抄了第二份 hex 的成因。

## 七、数字如何复核

本文所有数字由 `scripts/coupling-probe.cjs` 静态解析得出，可随时重跑：

```bash
node scripts/coupling-probe.cjs --root . --src src --out coupling.json
```

它量四件事，每件都直接对应一个决策：

| 量出来的 | 支撑的决策 |
| --- | --- |
| 死类名数与分布 | 能否安全清理；整文件搬 CSS 会不会把包袱发布出去 |
| 同一类名被几个样式表定义 | 谁是真源。**>1 即同名冲突**，胜负看 `@import` 顺序，不看文件职责 |
| 幽灵类名（用了但没定义） | 有多少 markup 的类名指向空 → 组件没有外观归属 |
| 完全重复的内联样式 | **重复处就是还没被抽象出来的组件边界** |
| import 入度为 0 的组件 | 已废弃，还是页面手写实现绕过了它 |

两个已知的判定边界（复核时会看到 ±1~2 个浮动）：

- **由模板串拼装的类名不可静态判定**，脚本把它们单独归入「不可静态判定」而非「死类」。若把组件 props 的枚举值补进脚本的 `EXTRA_DYNAMIC`，`icon-tile-green` 这类会从「死类」移到「不可判定」，死类数会少 1~2 个。
- **幽灵类名的数量对解析方式敏感**：`:class="…"` 属性里含有子串 `class="`，用朴素正则会把绑定表达式（`node.owned`、`currentSys.systemCode`）误算成类名。脚本已用否定后顾排除该形式；换成朴素正则时这个数会虚高到 90+。

## 八、不建议做的事

- **不要一开始就拆成独立仓库 / 发布独立 npm 包。** 组件契约尚未稳定，版本管理成本会立刻超过收益。
- **不要整文件搬运 CSS。** 会带进 103 个死类，并让 `components.css` / `pages.css` 的 46 处覆盖关系失去仲裁。
- **不要逐条打补丁修样式。** 325 处对比度不达标的根因只是一个 `--text-muted` 值；同类问题应当改源头。
- **不要在搬迁的同时改视觉。** 搬迁阶段的目标是「像素级不变」，视觉调整另开一轮，否则无法判断回归来自哪里。
