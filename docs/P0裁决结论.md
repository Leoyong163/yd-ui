## 2. P0-T1 · 回归基线

### 2.1 口径

与《前端样式与质量体检报告》保持一致，便于数据复用：

```
5 个导航页（首页 / 发起申请 / 审批中心 / 即将到期 / 我的权限）
× 3 视口（1440×900 桌面 / 768×1024 平板 / 390×844 移动）
× 2 主题（亮 / 暗）
= 30 组
```

### 2.2 采集内容

| 层次 | 内容 | 文件 |
| --- | --- | --- |
| 表现层 | 每个可见元素的**计算样式指纹**：46 个布局/外观属性 + 矩形坐标 | `baseline/styles/<key>.json` |
| 观感层 | 视口截图 + 内容全长截图 | `baseline/shots/<key>.png` / `<key>.full.png` |

**两个工程细节**（都踩过坑，已固化进脚本）：

- **指纹要按稳定路径索引**，用 `tag.class:同类序号` 从 `<html>` 拼出层级路径，不按数组下标。这样 DOM 顺序变化时才告警，无关改动不会误报。
- **截图不能只截一屏**。本项目页面滚动发生在 `.main-wrap` 这类**内部容器**上，`fullPage` 只能截到一屏。脚本改为把视口临时加到内容高度再截——宽度不变，所以不触发响应式断点，只是让滚动容器不再裁剪。

### 2.3 规模与自检

| 项 | 结果 |
| --- | --- |
| 组数 | 30 / 30 |
| 覆盖元素 | 6630 |
| 采集错误 | 1（首页一个资源 404，非功能性） |
| **确定性自检** | 用同一份代码独立采两次并比对：`DIFF_TOTAL = 0`（ADDED 0 / REMOVED 0 / STYLE 0 / GEOM 0 / COUNT 0） |

自检的意义：**证明这个门禁不会因为测量抖动而误报**。否则后面每次搬迁都会淹没在假阳性里。自检产物保留在 `.workbuddy/verify/after/`。

### 2.4 怎么用

```bash
# 采集现状
node scripts/p0-baseline.cjs --url http://localhost:5173/ --out .workbuddy/verify/after

# 比对（退出码 0 = 通过，1 = 有差异）
node scripts/p0-baseline-diff.cjs --base .workbuddy/verify/baseline \
  --next .workbuddy/verify/after --md .workbuddy/verify/diff.md
```

比对报告会指名道姓到「哪个元素、哪个属性、从什么变成什么」，分 ADDED / REMOVED / STYLE / GEOM / COUNT 五类。`REMOVED` 最危险——组件被换掉或条件渲染变了才会出现。

## 3. P0-T2 · 51 条同名冲突的裁决

### 3.1 关键发现：同名 ≠ 冲突

原探测脚本判定「同名冲突」的依据是「同一个类名被多个样式表定义」。但**规则形态**没被考虑进去，于是产生大量假警报。按形态重新分类后：

| 判定 | 数量 | 含义 | 处置 |
| --- | --- | --- | --- |
| **DUP_BASE 真冲突** | **13** | 两侧都定义了**本体配方**，后者静默覆盖前者 | 必须合并去重 |
| **SCOPED_ONLY 假冲突** | **35** | 一侧是本体配方，另一侧只是**页面容器内的局部微调** | 归属已明确，微调原样留宿主 |
| **SCOPED_BOTH** | **3** | 两侧都只是局部微调 | 各自保留，语义定归属 |

> 典型对照：`.btn` 在 components.css 是本体配方（`min-height` / `padding` / 状态分支），在 pages.css 只有 `.approval-actions .btn { min-height: 36px }`、`.expiring-role-actions .btn { … }` 这类**限定在页面容器内**的覆盖。二者不是竞争关系——前者是库的配方，后者是宿主在特定页面里的合理微调。把这类判成「必须合并」是错的。

### 3.2 真冲突 13 条（必须处理）

| 类名 | 共有样式表 | 实际生效者 | 与库的关系 | 处置 |
| --- | --- | --- | --- | --- |
| `active` | pages + components + layout | pages | **强相关** | 状态修饰类，**前缀化**（见 3.4） |
| `table-wrap` | pages + components | pages | **强相关** | 先合并；**库须采用当前生效值** |
| `tree-children` | pages + components | pages | **强相关** | 先合并 |
| `tree-row` | pages + components | pages | **强相关** | 先合并；grid 列宽两侧不同 |
| `main-content` | pages + layout | pages | 宿主内部 | 合并去重（P5 加锁时做） |
| `main-wrap` | pages + layout | pages | 宿主内部 | 合并去重 |
| `sidebar` | pages + layout | pages | 宿主内部 | 合并去重 |
| `sidebar-overlay` | pages + layout | pages | 宿主内部 | 合并去重 |
| `topbar` | pages + layout | pages | 宿主内部 | 合并去重 |
| `page` | pages + layout | pages | 宿主内部 | 合并去重 |
| `permission-detail-id` | pages + base | pages | 宿主内部 | 合并去重 |
| `user-id` | layout + base | layout | 宿主内部 | 合并去重 |
| `warn` | pages + layout | pages | 宿主内部 | 合并去重 |

**9 条是宿主内部的重复定义**（layout/pages/base 之间），与组件库无关，不阻塞 P1。

**4 条与库相关**，必须定下规则：

> **裁决规则：搬迁期一律以「当前实际生效者」为准。**
>
> 因为搬迁阶段的硬目标是**像素级不变**（规划 R2）。`tree-row` 的 grid 列宽在 components.css 是 `18px minmax(0,1fr) auto 52px`，在 pages.css 是 `20px minmax(120px,1fr) auto 56px`——后者才是屏幕上的真实样子。把类判给库时，库必须采用 **pages.css 的值**，同时删掉 pages.css 里重复的那份本体定义。
>
> 至于「20/56 还是 18/52 更好」是**设计问题**，属于搬迁完成后的独立一轮优化，不能混进来。

### 3.3 族裁决表（P0-T2 的最终产出）

按「同一控件的变体整族处理」原则，逐族落定归属：

| 族 | 成员 | 归属 | 实测依据 | 遗留动作 |
| --- | --- | --- | --- | --- |
| **按钮族** | `btn` `btn-primary` `btn-secondary` `btn-ghost` `btn-danger` `btn-sm` | **库** | 本体配方全在 components.css，含 3 条状态分支；pages.css 只有 4 处页面上下文覆盖 | 无 |
| **标签族** | `tag` + 14 个 `tag-*` | **库** | 本体配方在 components.css；与 `StatusTag`/`UrgencyTag` 绑定 | `tag-danger`/`tag-success` 无生产者，随组保留并标注 |
| **卡片族** | `card` `card-header` `card-title` `card-body` | **库** | 本体配方在 components.css | pages.css 的 3 处上下文覆盖保留 |
| **表格族** | `table` `table-wrap` `cell-name` | **库** | `table` 本体 18 条规则在 components.css | `table-wrap` **先合并**（真冲突） |
| **树族** | `perm-tree` `tree-*` `leaf` | **库** | 与 `PermissionTree` 绑定 | `tree-children`/`tree-row` **先合并** |
| **页签族** | `tabs` `tab-count` | **库** | 本体在 components.css | 无 |
| **分页族** | `pagination*` `page-btn` | **库** | 仅被 `Pagination.vue` 使用 | `.active` 需前缀化 |
| **表单控件族** | `input` `select` `form-field` `form-hint` `form-checkbox` | **库** | 控件语义，页面与组件都在用 | `textarea` 当前是死类，需确认是否启用 |
| **图标族** | `icon-tile*` | **库** | 与 `IconTile` 绑定 | `icon-3d*` 是旧类名别名（见 §6.2） |
| **反馈族** | `toast-root` `error-summary` | **不归库** | **实测两者都是死类，项目里没有对应实现** | 规划里「归库」的判断修正为「待建组件」 |
| **状态修饰族** | `active` `selected` `open` `done` `current` | **不归任何一方** | 它们是修饰语，不是组件 | **前缀化**（见 3.4） |
| **布局族** | `col-panel*` `list-item*` `three-col` `page*` `topbar` `sidebar*` `main-*` | **宿主** | 页面语义 | 无 |
| **文件族** | `file-*` | **宿主** | 只在 pages.css 定义，只被页面引用 | 无 |

### 3.4 `active` / `selected` 的处置方案

这两个**不是组件，是状态修饰语**。当前有 21 处 `.x.active` 的写法分布在 components/pages/layout 三方，谁定义谁生效靠加载顺序决定——这是最脆弱的一环。

**方案：前缀化，就地归属。**

```
.btn.active        → 由按钮族在库内定义
.page-btn.active   → 由分页组件在库内定义
.list-item.active  → 由宿主在 pages.css 定义
.tab.active        → 由页签族在库内定义
```

**执行时机**：P2 搬迁时同步改 CSS 选择器，**不新增一轮改动**。在此之前不动。

### 3.5 验证门

裁决表每一行都写清了「谁在用、归于何处、改动后谁需要跟着改」，无悬空项。证据可复核：`docs/P0-冲突类形态分析.md` 的第五节列出全部 51 条的形态计数。

## 5. P0-T4 · 死类处置

### 5.1 数字修正

原探测结果「198 条」是**唯一类名数**；展开成「样式表 × 类名」是 206 条记录。逐条确认后：

| 判定 | 数量 | 说明 | 处置 |
| --- | --- | --- | --- |
| **SAFE_TO_DELETE** | **135**（唯一名） | 字符串层面也无任何引用 | 可删（其中交互态类需先分废弃/待实现，见 5.4） |
| **ALIVE_LITERAL** | **42** | 在字符串里出现过，**探测器漏判** | 不可直接删，见 5.2 |
| **ALIVE_DYNAMIC** | 2 | `modal-lg` / `modal-xl`，由 `` `modal-${size}` `` 拼装 | 不可删 |
| **ANT_RUNTIME** | **23** | antd 运行时生成的类名 | **绝对不可删**，见 5.3 |

### 5.2 探测器漏判的 42 条：真实率约 57%

原探测器只扫「静态 class 属性」，因此**所有由模板串拼装、或写在 `:class` 数组里的类名都被漏掉**。确认后的证据（完整表见 `docs/P0-死类确认.md`）：

**确认为真类名（高置信，约 24 条）**——同一字符串里还并列着其它已知类名：

`route-apply-form` `route-approval` `sidebar-collapsed` `sidebar-open` `sidebar-overlay-open`（`Shell.vue` 动态生成）
`apply-cat-item` `approval-list-item` `approval-role-perm-trigger` `days-badge` `expiring-role-item`
`form-mini-select` `form-radio-option` `form-select-chevron` `form-select-dropdown` `identity-stat`
`item-role` `item-sys` `item-text` `permission-risk-label` `post-label-date-input-wrap`
`role-auth-dropdown-tab` `role-single-select` `system-pick-item` `current` `tab`

> 这 25 条如果照原清单删掉，会直接导致导航状态、列表选中态、下拉面板样式失效——**且不会报错**。

**疑似同名业务字符串（约 17 条）**，需 1 分钟人工扫一眼：`app`（实为 `#app` id）、`success` / `error` / `warning` / `info` / `pending`（状态枚举值）、`required`（表单校验规则）、`nowrap`（内联 style）、`textarea` / `toast`（`Inspector.vue` 的类型名）、`highlight`、`purple`、`row`、`unread`、`dark`（主题值而非类名）。

### 5.3 antd 运行时类名 23 条：删了会出事

`ant-checkbox*`（8）、`ant-form-item-label`、`ant-tooltip*`（3）、`ant-btn` / `ant-btn-primary`、`ant-select-*`（7）、`anticon`。

这些类名**从不写在模板里**，是 antd 自己生成的；我们的 CSS 在给它们上主题色。其中 `ant-form-item-label` 与 `ant-select-open` 明确带着**暗色主题覆盖**——删掉等于暗色表单立刻回退成默认配色。

> 这一条应写进组件契约（已写入 §4）：**库的样式层必须容忍 antd 的存在**，针对 `.ant-*` 的规则属于「给 antd 上主题」，是库的一部分。

### 5.4 删除前需分辨的第二种情况：样式已写好，但从未被激活

`SAFE_TO_DELETE` 里混着一批**交互态修饰类**。它们的特征是：CSS 写好了，但**没有任何代码会切换它们**——因为全文搜索连字符串都没搜到。

| 类名 | 本应表现 | 实测 |
| --- | --- | --- |
| `dragover` | 文件拖拽悬停时高亮 | `.upload-zone.dragover` 样式已写好，但 7 个表单页里的 `.upload-zone` 是**纯静态容器**（无 `input`、无 drag 事件、无 click），该类永不被添加 |
| `has-error` / `form-error` | 表单字段报错态 | 无代码切换 |
| `is-loading` | 加载态 | 无代码切换 |
| `leaving` / `done` | 进出场态 | 无代码切换 |
| `skeleton-*` / `spinner` | 骨架屏与加载指示 | 无实现 |

**这不是「死代码」，是「未实现的功能」或「已废弃的旧设计」。** 两者的删除决策完全不同：

- 若判定为**废弃** → 删，减少维护面；
- 若判定为**待实现** → **保留**，它是设计意图的落地锚点，删了将来还要重写。

> 建议先只删「有替代品」的（如 `icon-3d*` 已被 `icon-tile*` 取代、`flow-node`/`flow-diagram` 已由 `.flow-card` 系列取代），
> 而 `dragover` / `is-loading` / `has-error` / `skeleton-*` 这一批**挂起待定**，等产品侧确认上传与表单校验是否需要反馈态。
>
> 顺带一个值得单独立项的发现：**7 个表单页的文件上传区都是静态占位**，外观像可投递区域但没有任何行为。

### 5.5 删除执行方式（P1 执行，P0 只出清单）

两条硬约束：

1. **按样式表分组删，每删一张表跑一次基线比对。**
2. **不能整条规则删**——很多类名以**组合选择器片段**形式存在，例如 `.tag-approved, .tag-active, .tag-success { … }`。删 `tag-success` 只能移除该片段，整条规则要留给 `tag-approved`。

完整清单在 `docs/P0-死类确认.md` 的 `SAFE_TO_DELETE` 一节，按样式表分组，可直接照做。

## 7. P0-T6 · antd 与库的关系

**antd 保留，作为库的 `peerDependency`。**

依据：`ant-design-vue` 被 **18 个文件**直接引用（全部表单页），`main.ts` 还全量注册了 `Antd`。表单页的交互与校验构建在 antd 之上——「去 antd」是一件与抽组件库无关的独立工程，不应混进来。

| 项 | 决定 |
